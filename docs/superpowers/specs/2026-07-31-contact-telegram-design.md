# Отправка заявки с главной страницы в Telegram — Design

## Контекст и цель

Форма «Нужна нестандартная конфигурация?» на главной странице сейчас только
выводит заявку в `console.log`. Нужно отправлять заполненную заявку в один
фиксированный Telegram-чат через Bot API, не раскрывая токен в браузере.

## Выбранный подход

Добавить публичный серверный endpoint `POST /api/contact`. Клиентская форма
отправляет в него имя, компанию, телефон, email, описание запроса и два флага
согласия. Endpoint
повторно валидирует входные данные, проверяет same-origin, ограничивает частоту
запросов по IP и вызывает существующий `TelegramApi` из `@repo/telegram`.

Конфигурация берётся только из серверных переменных окружения:

- `TELEGRAM_BOT_TOKEN` — токен бота;
- `TELEGRAM_CHAT_ID` — идентификатор чата назначения.

Реальные значения не добавляются в репозиторий; в `.env.example` будут только
пустые шаблоны и комментарии.

## Поток данных

1. Пользователь заполняет форму и даёт оба обязательных согласия.
2. Браузер блокирует обычную отправку формы и показывает состояние отправки.
3. Клиент отправляет JSON на `/api/contact`.
4. Сервер проверяет origin, rate limit, JSON-схему и наличие конфигурации.
5. Сервер формирует HTML-сообщение, экранируя каждое значение формы, и вызывает
   `TelegramApi.sendMessage(TELEGRAM_CHAT_ID, text)`.
6. При успешном ответе Telegram сервер возвращает `{ ok: true }`; форма очищает
   поля и показывает существующее сообщение об успехе.
7. При ошибке сервер возвращает безопасное описание без токена и лишних деталей;
   форма сохраняет введённые значения и показывает сообщение об ошибке.

## Валидация и безопасность

- Сервер ограничивает `name` 120 символами, `company` 200, `phone` 50,
  `email` 320 и `message` 2000 символами; требует непустые `name`, `phone`,
  корректный `email` и оба флага согласия равными `true`. Необязательными
  остаются `company` и `message`.
- `Origin` должен совпадать с origin приложения. Для окружений без
  `NEXT_PUBLIC_BASE_URL` используется origin из входящего host, как в текущих
  публичных API routes.
- Rate limit — простой in-memory sliding window: не более 5 заявок с одного IP
  за 10 минут на экземпляр приложения. Это не механизм авторизации; при
  нескольких экземплярах лимит применяется отдельно на каждом экземпляре.
- Telegram получает только данные заявки и время отправки. Согласия используются
  для допуска к отправке и не передаются как отдельные поля.
- HTML-экранирование предотвращает подстановку пользовательских тегов в
  `parse_mode: HTML`.
- Токен не попадает в клиентский bundle, ответы API или логи.

## Обработка ошибок и UX

- Отсутствующая конфигурация — серверная ошибка конфигурации, отображаемая
  пользователю как временная невозможность отправить заявку.
- Ошибка Bot API или сети — ошибка upstream; пользователь видит нейтральное
  сообщение и может повторить отправку.
- Во время запроса кнопка отключена и показывает, что отправка выполняется.
- Повторное нажатие после ошибки возможно без повторного заполнения формы.

## Тестирование

- Unit-тесты серверного endpoint проверяют валидацию, same-origin, rate limit,
  HTML-экранирование, вызов Telegram и безопасные ответы при ошибках.
- Тесты компонента формы проверяют отправку валидных данных, состояния loading,
  success и error, а также сохранение данных при ошибке.
- Существующие тесты пакета `@repo/telegram` остаются зелёными; live-вызовы в
  Telegram в автоматические тесты не добавляются.

## Ограничения и осознанные отказы

Заявка не сохраняется в базе и не ставится в outbox: цель — простая доставка в
один чат, а не построение CRM. При необходимости гарантированной доставки или
истории заявок это будет отдельным следующим изменением.
